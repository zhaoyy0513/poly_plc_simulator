### 用户报的 bug：停用后刷新居然有数据

**根因是进程跑了旧代码，不是逻辑错。** 控制面进程 9:44 启动，`app.py` 15:19 才改——
磁盘上的 409 守卫根本没在运行。旧代码里停用的 link 被问状态时会去 probe，
`ModbusTcpClient` 发现 socket 关了就自动重连，所以点刷新**真的建了一条新连接**。

用户的判断是对的（"如果每次点击都创建一个 client 那就是有大问题"）。已确认
实际情况是：**每个实例只有一个 client，缓存在 `app.state.link_supervisors` 里复用**，
不存在按请求创建。停用后对端新增连接数实测为 0。

### 教训：改了 pyproject 或 app.py 后，`uv run` 才会重新解析/加载

`.venv/Scripts/python -m pytest` 用的是已经 import 好的旧模块，`uv run` 才是新的。
之前 poly-modbus 包名那次也是同一个陷阱（已记在 2026-10-22）。

## 第二轮：停用后详情页仍显示过期延迟/连接时长（提交 `1784a68`）

用户报：停用后详情页中间还有「连接目标 / 往返延迟 / 连接时长」，而实例没启动。

**根因不在 API。** 实测 `/api/servers/{id}`、`/values`、`/api/servers` 三处对
停用实例都正确返回 `latency_ms=null`、`started_at=null`。是前端把过期快照当现场：

1. `values` 是实时快照，轮询在 `running` 转 false 时就停了 → 快照停在最后一次
   活着的数据上。**在总览页停用再点「打开」**这条路不走 store 的 `updateServer`
   （不触发 `refreshValues`），快照原样带过来。
2. `values?.latency_ms ?? current.latency_ms` 的 `??` 再兜一次底。

结果：往返延迟显示停机前那一跳；连接时长以旧的 `started_at` 为基准持续往上走，
看起来连接一直活着。

**修法**：`store.loadServer` 在载入的实例不在运行时丢弃 `values`（实时快照不能
比它描述的对象活得更久）；`ServerPage` 的 latency/startedAt 改为按 `running` 取，
不靠 null 判断；新增共用 `isRunning(server)`（`enabled` 是期望状态、`status` 是
观测状态，每次起停都错开一拍，只信任何一个都会把过期值当实时值）。

**同类教训**：`a ?? b` 在「b 是上一次成功的值」时是个陷阱——null 是合法的
"现在没有"，不是"用旧的试试"。实时指标要用运行状态门控，不要用空值判断。

顺手去掉重复的「启用连接」：数据区阻塞面板里那个和页头电源按钮是同一个动作。
保留页头那个（所有 tab 唯一存在的电源控件），面板改成文字指向右上角。
